# PaneFlow 场景价值地图（结合实际需求）

> 承接 `docs/v5-compliance-and-value-audit.md` 的五条价值脉络。本轮把它们**落到具体场景**，并回答一个问题：PaneFlow 的独特架构，在**哪一类真实工作**上不可替代。
> 事实基座：`packages/server/src/orchestrate/builtin-templates.ts`（8 个内置骨架）、`roles.ts`（角色库）、`engine.ts`（引擎能力），均已逐行核对。

---

## 0. 核心诊断：引擎是产品级，骨架是演示级

先看一组量化事实——引擎实现了 4 个高级编排能力，但 **8 个内置骨架里的实际使用次数**是：

| 能力 | 引擎 | 8 个骨架中的使用次数 |
|---|---|---|
| 条件边 `condition` | ✅ 完整 | **0 次** |
| 检查门禁 `checks` | ✅ 四类 | **0 次** |
| 动态扇出 `expand` | ✅ 完整 | **1 次**（仅 generic-delivery） |
| 模板变量 `variables` | ✅ 完整 | **1 次**（仅 generic-delivery） |

再看骨架的**提示词**（`builtin-templates.ts` 原文）：

- `parallel-module-dev`：「实现一个简洁可运行的 HTTP API 服务（**语言自选**）」「**若无可自述假设**」「实现 3 个核心页面**雏形**」
- `standard-dev-flow`：「初始化一个标准工程项目（**语言/技术栈自选一个你最有把握的**）」
- `bug-fix-pipeline`：「构造一个可稳定复现的缺陷场景（**若无真实 bug，则人为注入一个典型缺陷再复现**）」
- `role-team-review`：「实现一个指定小功能（**自选：命令行 TODO 工具即可**）」

**结论：这 8 个骨架的拓扑设计是产品级的，但内容是"能在空目录里跑通的演示"，不是"能解决真实工作任务的场景"。**

三条推论：

1. **7/8 的骨架无法接收真实输入**——只有 `generic-issue-delivery` 声明了 `variables`，其余骨架连"把报错日志/需求编号/repo 列表传进去"的入口都没有。它们只能当演示跑。
2. **高级能力在真实场景中几乎闲置**——条件边和 checks 在真实 run 里从未出现过。不是引擎不行，是**没有场景把它们用起来**。
3. **角色库是设计稿的薄壳**——`roles.ts` 的 `Role` 只有 `id/name/agentKind/prePrompt/env` 五个字段；v4 §8 设计的「约定文档集 + 前置/后置动作 + 检查集 + 提示词骨架」**一个都没实现**。这意味着**角色目前无法承载领域知识**，只能当一段提示词前缀。

所以「从演示到真实工作」的缺口不是能力，是**内容**。而填内容这件事，成本远低于造能力。

## 1. 场景分层（按"距可用差什么"排）

### 第一层｜改提示词即可释放（0 新能力，0 新骨架）

拓扑已经对了，只需要把演示提示词换成真实工作提示词 + 接通参数。

| 场景 | 用哪个骨架 | 今天差什么 | 真实需求举例 |
|---|---|---|---|
| **S1 多仓服务并行交付** | `parallel-module-dev` | `cwd` 指向真实 repo；加 `variables`（issue 编号/版本/需求描述）；提示词去掉"语言自选" | 一个需求要同时改 3 个服务 + 1 个前端仓：现在是排队做人天，或一个人开 4 个终端手工协调。PaneFlow 天然四路并行 + worktree 隔离 + 汇总集成检查 |
| **S2 报错驱动的 Bug 修复** | `bug-fix-pipeline` | 把原始报错栈作为 `variable` 注入 `repro` 节点；提示词去掉"人为注入缺陷" | 测试/线上报错 → 复现 → 行级溯源 → 最小修复 → 全量回归。今天这四步全靠一个人在脑子里串 |
| **S3 团队标准交付流程固化** | `standard-dev-flow` + 角色库 | 把团队规范写进角色 `prePrompt` + Space 约定文档（`buildConventionBlock` 已能注入） | 每个新功能都要"建目录/装 lint/写测试/补 README/规范提交"——把这些固化成一条可复用的流水线，而不是每次重新交代 |

**这一层的价值**：投入最小、见效最快。三个场景加起来只需改 JSON 提示词 + 加 variables 声明，**一行业务代码都不用写**。它同时会第一次把 `variables`、`checks` 用起来（S1/S2 加建后置校验）。

### 第二层｜缺骨架，但拓扑与引擎已完整支持（新增骨架，无需改引擎）

| 场景 | 拓扑形态 | 用到的引擎能力 | 真实需求举例 |
|---|---|---|---|
| **S4 多仓/多目标健康巡检** | `expand` 按 repo 列表动态扇出 → 每路检查 → fanin 汇总 → 出报告 | 动态扇出 + checks + 定时（外挂 cron） | 10 个仓的依赖过期/安全漏洞/覆盖率下降/日志异常。今天是"想起来才查"，且没人愿意手工查 10 遍 |
| **S5 数据治理批次** | 多维校验并行（空值率/主键重复/枚举合法性/跨表一致性）→ 汇总 → 回填 → **逐条断言验证** | checks + 断言证据链 | **这一条直接对应你手上的活**：绿化台账汇总、`byRegion` region_codes 清理、GREEN_GROUP 项目名称回填——每个都是"校验 + 回填 + 验证"的同一模式。而数据治理最怕的就是**改了但不知道改对没有**——PaneFlow 的 `assertionResults` 逐条 evidence 正是解药 |
| **S6 多仓契约兼容验证** | 改上游契约 → 并行验证各下游调用方（编译/契约测试/mock 比对）→ 汇总不兼容清单 | 真实并行 + 断言核对 | 多服务改造最怕"改了上游忘了下游"。今天是靠人记 + 出事再回滚 |
| **S7 迁移/升级批处理** | 按模块扇出 → 每路改 + 自测 → 汇总 → 全量回归 | 动态扇出 + worktree 隔离 + 回归门禁 | JDK8→17、依赖大版本升级、废弃 API 替换——机械但面广，正是"人多不划算、人少做不完"的区间 |

**这一层的价值**：新增骨架 = 写一份 JSON + 一段提示词。**引擎一行都不用动**——因为这些能力（扇出/并发隔离/门禁/断言）都已经实现并通过测试了，只是没人用。

### 第三层｜与你既有治理体系咬合（价值最高）

| 场景 | 说明 |
|---|---|
| **S8 变更交付治理自动化** | 你手上的 `catalog + Change 包 + 三态门 + Issue Flow Console` 是一套**人为执行**的治理流程。PaneFlow 可以把"三态门"变成**机器执行**：一个 Change 包 → 并行审视（规范符合性 / 影响面 / 回滚方案 / 验收证据）→ 门禁判定 → 留档。这不是"用 PaneFlow 做别人的事"，是**让 PaneFlow 自动执行你自己的治理流程** |
| **S9 交付审计报告** | 把一次运行已经产出的证据链（`acceptance` × `assertionResults` × `run.events` × `outputSnapshots`）自动装配成一份可贴 PR、可附 Issue、**可直接进周报**的《交付审计报告》 |

**为什么这一层最高**：S8 与你的既有资产直接咬合（不用换赛道），S9 与你的岗位职责直接咬合（你是交付治理负责人，需要向他人证明"做到了什么程度"）。而且 S9 **零新引擎能力**——数据全在盘上。

### 第四层｜场景外延（探索更多可能）

| 场景 | 形态 | 价值判断 |
|---|---|---|
| **S10 故障复盘多路调查** | 一份告警 → 并行查日志/指标/变更历史/依赖链 → 汇总时间线与根因假设 | 中。与 bug-fix 同源，但产物是"复盘报告"而非"修复" |
| **S11 技术选型调研** | `research-compare` 扩成 N 路 → 决策报告 | 中。骨架已有，你自己做产品方向思考时就会用 |
| **S12 知识库/文档一致性治理** | 多篇文档并行校验（结构/失效链接/与代码不符）→ 修订清单 | 中。对位你维护的 llm-wiki |
| **S13 兼容性矩阵验证** | 多版本 × 多环境并行跑验证 | **高，且是差异化场景**——见 §2 |
| **S14 汇报材料聚合** | 把一批 run 的证据链聚合成周报素材 | 中。S9 的批量版 |

## 2. 差异化场景：只有 PaneFlow 能做的一类

前四层在回答"做什么"，这一节回答更关键的问题：**哪类工作，LLM-API 软编排根本做不到？**

PaneFlow 的三个硬性质——**真实终端隔离 / 确定性拓扑 / 证据链留档**——划出了一片独占区：

### 2.1 需要"真运行时"的场景（软编排无解）

LLM-API 编排的节点是"一次函数调用"，没有进程、没有工作目录、没有 TTY。凡是需要这些东西的场景，它天然做不到：

- **S13 兼容性矩阵**：并行验证"同一个改动在 JDK8 / JDK11 / JDK17 下是否都通过"——需要三个独立运行时环境同时存在。PaneFlow 的每个 pane 可以指向**不同的 Docker / 不同 JDK / 不同 worktree**（`splitPane` 的 `cwd` 参数 + 节点级 `env`）。**这是软编排结构性不可能的场景。**
- **交互式 CLI 驱动的任务**：数据库迁移、部署脚本、包管理器的交互确认——需要真 TTY。PaneFlow 的 pane 是真的终端，且 `blocked` 审批是原生的。
- **长时任务 + 中途人工介入**：交付类任务常在中间冒出一个必须人答的问题（"这个字段要保留吗？"）。`clarify` 循环 + `blocked` 审批是引擎级能力，不是补丁。

### 2.2 需要"确定性"的场景（AI 生成拓扑的系统不可用）

- **合规/生产变更**：拓扑必须可预演、可复现、可审计。`dry-run` 已能静态展开变量/条件/扇出并打印最终拓扑——**AI 动态生成 DAG 的系统无法回答"这次到底会执行哪些步骤"**。
- **团队流程固化**：流程本身是治理资产，不能被 AI 每次重新发明。

### 2.3 需要"证据链"的场景（软编排交付的是"它说它做完了"）

- **受审计的数据变更**：谁在什么时候改了什么、依据什么断言、证据是什么。`outputSnapshots`（终端快照）+ `run.events`（500 条事件）+ `assertionResults`（逐条证据）**三者叠起来就是一份可追溯的审计档案**。这不是"顺便记的日志"，是**可以拿出去给人看的证明材料**。

**一句话**：软编排卖的是"AI 帮你把活干了"；PaneFlow 卖的是"**活在一个你能看见、能干预、能留证的封闭环境里被干完了**"。后者的场景边界更窄，但在这个边界内**没有替代品**。

## 3. 场景 × 价值脉络矩阵

把场景和上一轮的五条价值脉络对上，看哪些场景能一次点亮多条：

| 场景 | ①证据链交付物 | ②CLI/headless | ③骨架流通 | ④规范执行器 | ⑤引擎可移植 |

| S1 多仓并行交付 | ● | ● | ● | ○ | |
| S2 报错驱动修复 | ● | ● | ● | | |
| S3 标准流程固化 | | ● | ● | ● | |
| S4 健康巡检 | ● | ●● | ● | ● | |

| S13 兼容性矩阵 | ● | ●● | | | ●● |

（●● = 强相关，● = 相关，○ = 弱相关）

**三个读法**：

- **S5 / S6 / S8 是"多点开花"场景**——它们同时吃掉证据链、headless、规范执行三条脉络，单场景的杠杆最大。
- **S9 是纯价值脉络 ① 的场景**，但它是**唯一零引擎改动**的高价值项，且直接对位你的岗位产出。
- **S13 是唯一点亮 ⑤（引擎可移植）的场景**——如果你认真考虑"引擎不只是 Herdr 的壳"，S13 是它的第一个真实用例。

## 4. 建议：先做哪三个

按「投入 × 杠杆 × 与你既有资产的咬合度」排序：

| 顺序 | 场景 | 为什么是它 | 投入 |
|---|---|---|---|
| **1** | **S9 交付审计报告 → 再扩成 S8 变更治理** | 零新引擎能力（数据全在盘上）；直接产出可交付物；是你岗位职责的自动化。S9 做完，S8 只是把"报告"换成"门禁判定" | 1–2 天 |
| **2** | **S5 数据治理批次** | 直接对应你手上的真实任务（台账汇总/名称回填/region_codes 清理）；断言证据链在这里的价值密度最高（数据治理最怕"改了不知道对不对"）；顺带把闲置的 `checks` 能力第一次用起来 | 2–3 天（含骨架与提示词打磨） |
| **3** | **S1 多仓并行交付** | 你每天都在做的事；拓扑已存在，只需换提示词 + 接参数；做完它，`variables` 能力第一次有真实用例 | 0.5–1 天 |

**共同前置只有一件**：让骨架能参数化（给骨架加 `variables` 声明）。这件事今天只做了 1/8，而它是所有真实场景的入口——**没有参数，骨架永远是演示**。
