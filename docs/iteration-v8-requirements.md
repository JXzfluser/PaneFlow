## 一、目标：v8 到底在干什么

### 1.1 目标锚定

| 层 | 内容 | 变化 |
|---|---|---|
| **北极星（项目级）** | AI 劳动的信任层——「AI 干的活能不能信」：规格/隔离/验证/存证/问责五原语 | 不变 |
| **阶段目标** | v7：把被证明能用的机器变成愿意天天用的工作台（A 组已交付；B/D 待裁决） | 承接 |
| **本迭代目标（v8）** | **真实地干一单活**：一条真实任务从真实载体进入（GitHub issue 原文，不是手抄摘要）、以真实交付物离开（可被人类 review 的 PR + 产物货架）、且下一单比这一单快（跨 run 记忆）。链路的三个断点——入口断、出口断、复利断——逐一接通 | 唯一任务 |

### 1.2 一句话读法

v7 回答「日常敢不敢把活放上来」，v8 回答「活放上来之后，链路自己走不走得完」。代码实况盘点给出的三行判断：**入口断**（issue 正文进不来、7/9 骨架无变量，"修 #308"从第一步靠人手抄）、**出口断**（done 的判据是终端空闲、产物落在 `.herdr/` 无人认领、全仓无 `git push` 无 `gh pr create`——"可交付物"今天产不出来）、**复利断**（跨运行零记忆、skills 是死配置、重启丢 blocked，每次都像新单）。v8 的所有需求只服务这三个断点的接通，其余一律不做。

### 1.3 全链路实况速览（2026-09-18 盘点，证据见 §三）

| 环节 | 状态 | 一句话 |
|---|---|---|
| 任务入口 | 半截 | 一句话下发已通（dispatch），issue 只能回写不能读取，无队列/定时 |
| 任务→流水线绑定 | 有缺口 | Planner 选模板已通；7/9 骨架无输入面，引用失败静默 |
| 运行中 | 基本可用 | 事件/时间线/审批/retry/resume 全通；reconciler 死码、重启丢 blocked |
| 完成与交付 | **断** | idle=done、fallback 假 done、产物无货架、无 push/PR——出口整段缺失 |
| 事后 | 半截 | 成本/导出/归档已通（v7-A2/A3）；跨运行记忆为零 |
| 无人值守 | 单 run 内达标 | run 内全自动；跨 run（重启、批量、定时）全无 |

## 二、支柱与需求映射

```
目标：闭环生产力（真实任务进 → 可信交付物出 → 下一单更快）
 ├─ 支柱〇 信任底线 —— done 必须意味着"验过"，中断必须接得回   → F1, F2, F3
 ├─ 支柱一 任务进得来 —— 真实载体成为一等输入，一单可变一批      → G1, G2, G3
 ├─ 支柱一·五 契约先于执行 —— 接单的标准立在派活之前            → M1, M2, M3, M4
 ├─ 支柱二 交付物出得去 —— 链路终点是人类可 review 的 PR + 货架  → H1, H2
 ├─ 支柱三 复利攒得下 —— 经验/配置/成功自动流向下一单            → I1, I2
 └─ 地基扫尾（v7-E 余项）                                       → E'
```

### 2.1 Genspark 对照（第三轮：全链路运营视角，只留可迁的）

| Genspark 的成熟处 | 对链路的启示 | 转译到 PaneFlow | 判定 |
|---|---|---|---|
| 单一输入框 + 自动规划：任务载体多样（链接/文件/网页），产品替用户把「需求原文」喂给 agent | 我们的 dispatch 已经是"自动规划"，缺的正是载体——issue 正文是真实需求的原生格式 | `gh issue view` 读取端点 + issue 内容成为一等上下文变量 | **真抄**（G1） |
| Workspace 任务板：多任务并行排队，状态一目了然 | run 直接进内存 Map，无队列概念；批量同类任务（issue 列表）无法一次派发 | 空间级轻队列（并发上限=营地上限），批量派发=一列任务展开 | **真抄**（G3） |
| 交付物货架：产物以文件卡片呈现、可点开可下载，交付「看得见」 | 产物躺在 `.herdr/artifacts/` 里，UI 无入口、无下载 | 产物端点 + 运行详情「交付物」区块（接 B3 货架的产物层） | **真抄**（H2） |
| 交付物回到真工具（Office 插件字节级 round-trip）——v7 立约「可原样打开」未实现 | 代码工作的「真工具」就是 git/PR：交付=分支上的一次可 review 变更，不是本地 commit | 引擎收口 `git push` + `gh pr create`，PR 链接上账，置于审批门内 | **履约**（H1，v7 契约的兑现） |
| 「敢收费、收得到费，才是真 Agent」——收费的本质是对交付质量作承诺 | 本地等价物不是钱，是**判据**：不把关过的活标成 done 就是虚假交付。Genspark 被骂最狠的正是交付注水 | 验收机器门泛化：`assertionResults` 有非 ok 即不得判 done；fallback 产物降级警示 | **抄承诺、抄反面**（F1） |
| Skill/智能体生态（对话生成、复用） | v7-B4 已立「技能卡」；缺的是**自动**——成功 run 的经验不用人点按钮就流向下一单 | skills 配置消费接线 + 同模板上次画像自动注入 | 承接+自动化（I1/I2） |
| 单输入框、零门槛下发（无人工契约环节） | 代价正是评测骂最狠的「交付注水」——不前置立约，后端用口碑还债 | **抄反面**：friction 前移——接单重（契约双向确认，M1），执行轻（少打断） | **反面教材**（M1） |
| Devin Playbooks/Knowledge：程序性 SOP 与按 repo/路径自动附加的规范并存 | 规范有两种形态：怎么干（模板）+ 在哪守什么规矩（作用域规则）；我们的 conventionFiles 无作用域无触发 | rules 作用域化（M3），repos 死配置转职责 | **真抄**（M3） |
| Manus/harness 计划确认环：复述需求→todo→人确认才动手（计划即契约） | 契约必须双向确认，不是单方注入——引擎已埋 align/clarify 半件，缺「门」的地位 | 升格为入口门（M1/M2） | **真抄**（M1） |
| 云端电话/公网发布/积分制/托管 | 无单机对应物（v7 判决不变） | — | **不迁** |

## 三、需求详述

### 批次 F · 信任底线【P0，不赌裁决，即刻可做，~1.5 天】

**F1 · 完成判据的机器门：done 必须意味着「验过」【P0】**
证据：done 判据 = herdr 报 idle（`engine.ts:1314`），不看内容；产物读不到时用终端尾部 5 行冒充 summary 仍判 done（`engine.ts:1396` `source:'output-fallback'`）；`validateAcceptance` 只校断言列表形状、从不核对 `status`（`shared/dag.ts:189-208`）；「断言全过」的机器判据全项目只在 9 号骨架里硬编码一条 `node -e`（`builtin-templates.ts:445-451`）。
需求：把 9 号骨架里的私有判据**泛化为引擎一等概念**——凡 run 内产物携带 `extra.assertionResults`，存在 `status:'fail'` 即节点不得判 done（标 `blocked` 等人工 or `failed`，取其一，实施时定）；`output-fallback` 产物在节点卡与运行卡上出 ⚠ 标记、不计入「绿灯」依据。不改 `validateAcceptance` 的形状校验语义。
验收：fake-ops 测试两例（fail 断言拦住 done；fallback 产物带警示）；9 号骨架改接引擎泛化判据后原 e2e 不回退。

**F2 · 等审批的 run 重启可活【P1】**
证据：boot 把所有磁盘 `running` 记录强制标 `failed`、working/blocked 节点一律标 failed（`engine.ts:86-100`）；审批等待是纯内存 `blockedWaiters`（`engine.ts:66`），服务重启即蒸发——**隔夜跑长任务 + 白天重启维护 = 等审批的单全丢**，这正是 Gate 0 隔夜运行的真实场景。
需求：blocked 节点重启后标 `paused`（新节点态，run 态保持 `running` 之外的次态或标 `blocked`），审批端点对重启后的 run 重新可等待；不追求恢复执行中的节点（herdr pane 已死，恢复=续跑语义，走 A5 ⤴）。
验收：重启前后 blocked run 状态一致可批；测试覆盖 boot 分支。

**F3 · 死码裁决（并入 v7-E 余项）【P2】**
证据：`startReconciler`/`reconcile` 零调用点（`engine.ts:1421-1433`，`PF_RECONCILE_MS` 挂起项同源）；`api/notifier.ts` 全模块仅剩自身测试引用（通道层接管后成孤儿，`channels.ts` 已含 settings.json 一次性迁移）；`engine.ts:57-60` 注释仍称 "M1 serial scheduling" 与并行实况矛盾。
需求：reconciler 接线带守卫或删除（裁决前维持挂起）；notifier 模块与其测试一并移除（迁移逻辑已在 channels，无损失）；过时注释修正。

### 批次 G · 任务进得来【Q1=是 后开工，~3 天】

**G1 · Issue 读取器：真实需求载体一等化【P0，入口断的正解】**
证据：GitHub 链路只有写——create-issue（`http.ts:273-300`）、update-issue（`:302-327`）；全仓无 `gh issue view`；`issueId` 只是透传字符串（`TasksView.tsx:89-96`），`{{issue_id}}` 只用于回写不用于读取需求。
需求：`GET /api/issues/:n`（gh --json，复用 GH_TOKEN 链）；下发时贴 issue URL/编号自动拉正文+评论注入 run 上下文（约定字段如 `{{issue.body}}`，走既有变量机制）；TasksView 输入框识别 issue 引用并预览。
验收：#308 类任务从「贴一个链接」到 run 启动零手抄。

**G2 · 骨架输入面补全 + 引用失败可见【P1，= v7-B2 承接扩容】**
证据：9 个内置模板仅 2 个声明 `variables`（`builtin-templates.ts:397,474`）；`applyVariables` 未命中的 `{{ref}}` 原样留在 prompt（`shared/dag.ts:443-446`）——agent 拿到花括号是静默事故。
需求：逐骨架声明输入点（v7-B2 原样）+ 新增：运行启动前对 graph 内未解析 `{{}}` 做 lint，warn 级事件上时间线（不拦跑，与 B2 的 RunDialog 必填校验互补）。

**G3 · 轻队列与批量派发【P2】**
证据：无 task/queue 概念，run 直接进内存 Map（`engine.ts:62`）；无定时/入站触发（server 侧无 setInterval/cron，`Console.tsx:92,194` 的轮询在前端）。
需求：空间级队列（待启 run 排队，并发上限可配、默认=营地上限）；批量派发=一个模板 × 一列 issue 编号展开 N 个排队 run（G1 的乘数效应）。定时/入站 webhook 不做（愿景 §3 值班表是 bot-space B3 的事，队列是其地基）。

### 批次 M · 契约前置：接单的标准立在派活之前【G1 同门槛（Q1=是），~3 天，v0.2 评审增补】

> 命题：G1 让 issue 原文进得来，但没回答「原文不合格式怎么办」。真实任务十有八九是模糊需求——没有接单门，垃圾进就是垃圾出，烧的还是真 tokens。业界共识（Cursor rules 分层触发 / Devin playbook+knowledge / Manus 计划确认环）指向同一件事：**执行前存在一份双向确认的契约，且契约本身机器可消费**。本批次把 v8 的「规格」原语从口号做成闸门。引擎地基已有一半：align 节点 + `aligned==='true'` 约定 + clarify 补齐循环（`validateAcceptance` 错误信息注释明写供 clarify 复用，`shared/dag.ts:187`）——缺的是门的位置。

**M1 · 接单门（DoR 检查）【P0，本批核心】**
需求：dispatch/运行启动前对「这单活」做适配性判定——(a) 输入含可机检的「验收标准」小节则提炼为断言面；(b) 不含则 align 节点**自动生成候选断言 + 澄清提问清单**，run 停在契约确认门（blocked 的一种，语义区别于执行审批）等人工批准/回抛给需求方；(c) 契约未确认，下游 impl 一律不派。三档处置按约束类别：**拦**（无契约不进）、**警**（时间线事件）、**谈**（clarify 双向）——不是只有硬拦一种。
验收：一条无验收标准的伪 issue → run 停在契约门且提问清单可见；补齐标准后放行跑通。

**M2 · 契约成为 run 的一等公民【P0，与 F1/H1 共用骨架】**
需求：run 首个结构化产物 = 契约对象（断言清单 + scope 边界「不动哪些」+ 预算上限 + 目标仓/分支），持久化在 RunRecord、卡片面可见（"这单按什么约定在干"）；F1 的验收机器门、H1 的交付守卫、B5 的预算顶**都引用同一份契约**——三处约束从三个孤岛变成一份契约的三个执行点。这是北极星「规格」原语的落地形态。
验收：F1/H1 的判定文案能指回契约条目（"AC-3 未过"而非"某断言失败"）。

**M3 · 规范作用域化：conventionFiles 升级为 rules【P1】**
证据：现状只有 space 级全量注入（`roles.ts:40-62` → `engine.ts:1199-1217`），无 repo/路径作用域、无触发条件；`profile.repos` 零消费（I1 曾问去向——答案在此：它是作用域的挂载点）。
需求：v0 保守形——rules 条目 `{repo?, pathsGlob?, file, note}`，节点按其目标仓/路径拼装注入（对齐 Cursor 的 glob 触发与 Devin knowledge 的自动附加）；旧 conventionFiles 字段兼容读取并自动迁移为无作用域条目。不做规则编辑器，配置文件即可。

**M4 · 接单模板回写：让烂需求自动触发 clarify【P2】**
证据：GitHub 写链路已有 create-issue 地基（`http.ts:273-300`）。
需求：一键向目标仓回写带「验收标准」锚点段的 ISSUE_TEMPLATE（格式与 M1 的机检锚点同源）——不在源头筛掉需求，而是让源头质量可检。顺手价值：模板本身就是给人看的 DoR checklist。

**M5 · 判例式规范（钩子，不排期）**：从历史驳回与断言失败中聚合「隐性规范」提案（哪类断言在这个仓反复 fail → 建议进 rules）。对应 bot-space「梦境模式」，契约数据面（M2）是其地基。

### 批次 H · 交付物出得去【Q1=是 后开工，~3 天，出口断的正解】

**H1 · PR 交付链：让链路终点是人类可 review 的东西【P0，v8 招牌】**
证据：全仓 grep 无 `git push`、无 `gh pr create`；收口只有 `git add/commit` + `gh issue comment`（`builtin-templates.ts:373`）——活干完留在本地，对协作方等于没干。能力地基其实已通：GH_TOKEN 注入（`github-cred.ts:29-35`）+ 网络域放行 github（`engine.ts:799`）+ agent 全权限运行（`--dangerously-skip-permissions`）。**自查修正（控制面实况）**：`:799` 是网络域名白名单不是命令白名单——引擎技术上拦不住 pane 内的任何命令，「只推工作分支」必须是编排层的真约束，不能只写在提示词里。
需求：push+开 PR 作为**带 manual check 门的交付收口节点**（人工放行那一次才推）；分支约束落在引擎侧：交付节点的目标分支由 runId 生成，push 前引擎在 workspace 内做 `git rev-parse --abbrev-ref HEAD` 守卫核验，不符即 blocked 不静默；wrapup 约定产出 `pr_url`，RunRecord 增列并上运行卡（绿灯判据的最后一公里）；首单在用户授权仓库人工盯完成。
红线：prompt 与守卫两侧都不给「推 default 分支」留路径；与 v7-B5 三态审批同机制（B5 若未做则保持逐次弹窗，不互锁）。

**H2 · 产物货架：交付物看得见【P1，接 B3 货架】**
证据：产物落用户仓库 `.herdr/artifacts/`（引擎自动 gitignore，`engine.ts:350-358`），无列表/下载端点；真删除记录时明示不清理产物（`RunsCenter.tsx` 确认弹窗文案）——产物生命周期无设计、只有默认。
需求：`GET /api/runs/:id/artifacts`（列表+元数据）与单文件读取（root 内路径校验，复用 fs 路由既有守卫模式）；运行详情加「交付物」卡片区（B3 三层货架的产物层）；真删除联动：可选一并清理 `.herdr/artifacts/<runId>`（默认不清，勾选才清）。

### 批次 I · 复利攒得下【Q1=是 后开工，依赖 B1/B4，~2 天】
