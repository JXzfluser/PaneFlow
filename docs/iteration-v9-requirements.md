## 总目标

把 PaneFlow 从「能跑通的编排器」推进到「小白敢用、越用越聪明的私人工作流」：
**一句话进、验收出、知识留、班底熟、接入快**。

判断一个需求是否属于 v9，只问一句：它是否让上面五个短语中的至少一个成为用户可感知的现实？

## 支柱一：一句话接单（N）——入口贴合小白

真场景：用户只会打一行字；但一条能编排的 issue 需要大量项目上下文补充。
现状证据：`POST /api/dispatch`（http.ts:682）已有 M1 接单门——正文含「验收标准」小节才直接成契约，
否则要求人补；任务页（TasksView.tsx）输入框与队列卡都没有「下一步」。

- **N1 需求增强器**：`POST /api/issues/enhance { text, deep? }`。
  服务端读空间上下文（cwd 的 README/最近 run 摘要/ISSUE_TEMPLATE/rules 摘要 + wiki 读回见 K2），
  经网关 chat completion 扩写为结构化 issue 正文（现状/目标/边界/验收草案）。
  浅档=单次扩写；深档=2 个候选拆解 + 一次自评选优（ToT-lite，成本 ≤3 调用，默认浅）。
  网关未启用 → 400 明说「先启用网关」。UI：任务页输入一句话 → ✨ 增强 → 可编辑预览 → 建单入编排。
  验收：单测（上下文装配、网关关闭 400、响应形制）+ 实机一次真扩写。
- **N2 DoR 门改版**：接单门缺「验收标准」时不再只是问人——先调 N1 自动补一版供确认，补不出才问。
  验收：dispatch 预览响应带 `autoFilled` 标记；机检缺项→自动补→仍缺→问，三级序列有单测。
- **N3 排队可见即可动**：queued run 卡片必须给出原因（并发额度占用者是谁）与动作（派发优先/取消）。
  现状是「2 排队中 · 无活跃任务」这种死局观感（2026-09-19 用户截图）。
  验收：queued 卡渲染等待原因 + 两个可点动作；有测试锁渲染条件。
- **N4 三步新手路径**：任务页首屏重构为「说一句 → 确认 → 开跑」三步；向导/提示围绕这三步，
  高级字段全部折叠。验收：首屏无未解释术语；快照测试锁结构。

## 支柱二：班底名册（B）——角色库真正发挥作用

现状证据：全局角色库（/api/roles）与空间弱绑定，节点选角色靠手挑；用户判断「没有发挥作用」
（2026-09-19）。bot-space 愿景里「持久数字员工」需要名册载体。

- **B1 空间班底 team[]**：SpaceProfile 增 `team: { roleId, alias?, note? }[]`；
  PUT /api/spaces/:id 白名单放行 + 结构机检；内置「标准五连」模板（规划/实现/评审/验收/沉淀，
  映射现有 prePrompt+agentKind），新空间一键装填。
- **B2 编排绑班底**：dispatch/planner 生成骨架时只从本空间班底取角色，节点自动带 `role`；
  空班底 → 回退旧行为并在预览里明说。验收：带 team 的空间下发，图上 agent 节点 role ∈ team（单测）。
- **B3 成员卡 UI**：设置页空间区增「班底」——列成员、选角色、改昵称、移除、单人试跑
  （= 单节点 run 复用现链路）。

## 支柱三：知识复利（K）——LLM wiki 沉淀回 GitHub

现状证据：H2 产物货架只在本机；跨运行记忆（I2）只见同空间 RunRecord；用户点名 GitHub wiki +
llm-wiki 风格（2026-09-19）。wiki 本质是 `<repo>.wiki.git` 独立仓库，PAT 可 push。

- **K1 wiki 写入器**：done 且验收全过的 run → 一键「沉淀」：契约+验收结论+经验条目蒸馏成
  带 frontmatter/双链的 md 页，浅克龙 wiki 仓库→写页→commit→push。
  **门控**：先查仓库可见性，public 仓库须用户显式确认（wiki 对全世界可读）。
- **K2 wiki 读回**：N1 增强上下文注入本空间相关 wiki 页（dataDir 内浅克龙缓存，按需 pull）。
- **K3 沉淀策略门**：自动沉淀默认关；只沉淀「绿 run + 用户点赞」，宁缺毋滥。
  验收：K1 单测覆盖 形制生成/无凭据 400/可见性警示；push 真链路留实机（失败可见不吞）。
