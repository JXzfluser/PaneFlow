# Bot 空间 v2：既有编排系统的自然延伸（评审稿 · 未提交）

> v1 评审结论：① 把"run 结束回收工作区"的资源决策误读为缺陷——实际上**跨 run 产物记忆已经存在且被真实复用**（Planner 复用上一轮 explore.json 是实证）；② 把角色库描述为待"升格推翻"的旧物——实际它是空置待用的地基。v2 修正定位：**Bot 空间不是新方向，是把已有资产从"按 run 组织"重述为"按居民组织"的一层视图与三个小能力**。

---

## 0. 事实基线（先承认已有的）

| 已有能力 | 实证 |
|---|---|
| 跨 run 产物记忆 | `.herdr/artifacts/` 已有 11 份产物；上次下发 Planner 真实复用了 explore.json 与 handoff_summary |
| 交接摘要机制 | wrapup/align 节点自发产出 handoff_summary.md，成为后续 run 的上下文 |
| 角色/人格地基 | 全局角色库（roles.json）+ 约定文档注入 + 网关模型路由 |
| 常驻能力 | herdr Pane 本来就是常驻进程（我们现在的回收是主动选择，不是技术限制） |
| 触发雏形 | 智能下发 = 人工触发；飞书出站通知已通 |

**v1 的错误**：把以上说成"缺失"，然后提出一堆"补齐方案"。**正确的说法**：以上已经在工作，Bot 空间只是给它们**一个面向用户的组织形态（通讯录）+ 三个增量能力（常驻/日程/消息）**。

## 1. Bot 解剖学（v2：在既有对象上加三个字段）

一个 Bot = **一个常驻 herdr Pane + 一份扩展的角色档案**。不新造对象，只扩两处：

```yaml
# roles.json 条目扩展（向后兼容：现有字段全部保留）
id: xiaozhuang
name: 小庄
agentKind: claude
prePrompt: …                    # 已有
env: …                          # 已有（网关注入）
# ↓ 以下为 Bot 化新增（全部可选，缺省行为与现状完全一致）
persistent: true                # 常驻：run 结束转 idle 待命（默认 false = 现状）
territory:                      # 领地（可选：不填则每次按 run 分配）
  repos: [service-order]
memory:                         # 记忆（可选：不填则维持 artifacts 现状）
  injectLast: 3                 # 唤醒时注入最近 N 份工作日记
schedule:                       # 日程（可选：B3 再实现，先留字段）
  - cron: "0 9 * * 1-5"
    task: 巡检仓库并汇报异常
```

## 2. 三个增量能力（每项都标明复用了什么）

| 能力 | 复用 | 真正的新代码 |
|---|---|---|
| **常驻**（run 结束 bot 转 idle 待命） | herdr Pane 常驻能力、引擎的营地上限（超员 LRU 焚毁，防资源失控） | 一个开关 `persistent` + 引擎 finally 分支不 close 而转登记 |
| **通讯录**（空间视图「居民」页） | 运行中心的卡片 UI、agentStatus 实时状态 | 居民列表视图 + 直达 pane 按钮 |
| **唤醒对话**（不走 run，直接 @它） | 终端预览的 send-keys/input 端点（已有） | 居民卡片上的输入框 |

日程（cron/事件触发）与消息总线放 B3——先让常驻与通讯录跑起来，看真实使用再决定值班表形态。

## 3. 场景（修正后：每个都标注与现状的关系）

- **Bot 通讯录**：空间里能看到小庄（claude·后端·idle）、小研（opencode·调研·working）…点击直达它的常驻终端。**现状已能看到 agent 列表，缺的是"按居民组织 + 常驻"**。
- **续聊**：run 结束后对小庄说"把刚才的接口再加个分页"——它记得上一轮（记忆注入）。

<!-- REVIEW: 以下场景在评审通过前保持占位，逐条过 -->

- **信任评级**：bot 履历（验收通过率/驳回数）自动聚合，Planner 按资历派活——数据已在 RunRecord 里，只差聚合视图。
- **值班表**：工作日早九点巡检 bot 自动巡逻仓库出报告；GitHub Issue 打开唤醒值班 bot。
- **招聘/解雇**：从 GitHub 导入别人的 .bot.yaml；连续驳回超阈值提醒是否换 bot。
- **梦境模式**（畅想档）：空间空闲时低优先级 bot 自主整理记忆/补测试/重构，早上收报告。

## 4. 与既有工作的关系（承接，不否定）

| 既有资产 | 在 Bot 空间中的角色 | 变化 |
|---|---|---|
| 编排引擎/骨架 | 不变——run 依旧是 bot 的工作方式 | 零改动 |
| 智能下发 | 下发 = 给 bot 派活；Planner 可按居民状态分配 | 零改动 |
| 角色库 | Bot 的前身；`persistent` 等新字段为可选扩展 | 向后兼容，现有条目零迁移 |
| 运行回收 | 资源策略保留（非 persistent bot 照旧焚毁） | 仅 persistent 分支新增 |
| 飞书通知 | bot blocked/完成照常推送 | 零改动 |
| OmniRoute | 模型与记忆底座 | 零改动 |

**一句话**：现有系统已经是"无居民的 Bot 空间"——每个零件都在，缺的只是把居民留下来的三个开关。

## 6. 评审确认点

1. `persistent` 默认值：默认 true（ bot 空间定位）还是默认 false（维持现状、显式开启）？建议默认 false，通讯录里一键转常驻。
2. 常驻 bot 的安全：常驻 = 常驻可注入终端，是否接受"远程模式下常驻 bot 自动降级为焚毁"？
3. 记忆注入来源：OmniRoute memory（依赖网关）还是本地 `.herdr/diary/`（零依赖）？建议先本地。
