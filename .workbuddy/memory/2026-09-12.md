- **工程成熟度 ★★★★☆ / 产品成熟度 ★★☆☆☆**。引擎与 herdr 终端底座是产品级资产，外壳还是单机自用工具级。

## 本次新发现的 P0 缺陷（此前文档未记录）

1. **画布往返静默销毁数据**（`packages/web/src/store.ts`）：
   - `toGraph()`（253-268 行）**不输出 `graph.variables`** → 旗舰骨架 `builtin-generic-issue-delivery`（`builtin-templates.ts:396` 声明了 `issue_id`）在画布打开并保存后，参数声明永久丢失，提示词里 `{{issue_id}}` 变成字面量喂给 Agent。
   - `dagToRf()`（103-108 行）与 `toGraph()`（262 行）**均丢弃 `edge.condition`** → 条件边在画布上不可达且手写即被销毁。
   - `toGraph()` 重建 metadata（263-266 行）时**丢掉 `description`、重置 `createdAt`** → 直接击穿智能下发的 Planner 选型（`http.ts:343-346` 正是读 `metadata.description`）。
2. **旗舰骨架默认并发写同一 cwd**：`engine.ts:873-920` 的 `expandFanout` 克隆节点不换 cwd，而设计 D8 的 worktree 隔离**全仓零实现**（ripgrep `worktree` 仅命中无关注释）→ 最核心的交付能力本身就是并发覆盖现场。据此建议把 v4 §9 中的 worktree 项**从 P2 上调至 P0**。
3. 安全面：API 无鉴权、`/api/fs/read` 的 root 由客户端提供（等价任意文件读）、`input` 端点可向终端注入文本、`index.ts:37` host 硬编码 127.0.0.1（v4 承诺的 `--host` + 令牌未实现）、Fastify `logger:false` 无结构化日志。
4. 运行历史硬截断 50 条（`store.ts:163`）；模板高级能力（condition/checks/expand/variables）除 expand 外**全部无 UI**（`PropertyPanel.tsx` 连 fanout 分支都没有）；画布无自动保存；`/api/fs/browse` 后端有、前端零调用。
5. 文档漂移：`PropertyPanel.tsx:82` 写「0=默认15分钟」，实际默认 30 分钟（`index.ts:22`）。

## 方法论备忘（下次复核可直接复用）

- **不要用 macOS BSD `grep` 的 `\|` 交替语法**——它在 BSD grep 下是字面量，会产生**假阴性**。必须用 ripgrep（Grep 工具）或 `grep -E`。本次第一轮 grep 因此误判，已重核。
- 评估"能力是否可用"要分三列看：**引擎实现 → UI 可达 → 画布往返安全**。PaneFlow 的缺口几乎全部集中在后两列，这是"文档说已实现、用户却用不上"的根因。

## 第三轮（22:10）· 场景价值地图（结合实际需求）

用户要求把价值脉络**落到真实场景**并探索更多场景。产出：

- 新增 `docs/scenario-value-map.md`（四层场景分层 + 差异化独占场景 + 场景×价值脉络矩阵 + 三个优先场景）

### 核心诊断（量化，本轮新发现）

**引擎是产品级，骨架是演示级。** 8 个内置骨架中四个高级能力的实际使用次数：**condition 0 次 / checks 0 次 / expand 1 次 / variables 1 次**；**7/8 骨架无法接收真实输入**（只有 generic-issue-delivery 声明了 `variables`）。

骨架提示词原文即证据（`builtin-templates.ts`）：「语言自选」「若无可自述假设」「实现 3 个核心页面雏形」「若无真实 bug，则人为注入一个典型缺陷再复现」「自选：命令行 TODO 工具即可」。

→ 结论：**从演示到真实工作的缺口不是能力，是内容**。填内容（改提示词 + 加 variables）成本远低于造能力。

另一发现：**角色库是设计稿的薄壳**——`roles.ts` 的 `Role` 只有 `id/name/agentKind/prePrompt/env`；v4 §8 设计的「约定文档集 + 前置/后置动作 + 检查集 + 提示词骨架」一个都没实现 → 角色目前无法承载领域知识，只能当提示词前缀。`buildConventionBlock()`（约定文档注入，单文件 100KB / 总 250KB 上限）是唯一的知识注入通道。

### 四层场景分层

- **第一层（0 新能力，改提示词即可）**：S1 多仓服务并行交付（`parallel-module-dev` 换提示词 + cwd 指向真 repo + 加参数）· S2 报错驱动 Bug 修复（报错栈作为 variable 注入 repro）· S3 团队标准流程固化（规范进角色 prePrompt + 约定文档）
- **第二层（缺骨架，引擎已完全支持，0 引擎改动）**：S4 多目标健康巡检（按 repo 列表动态扇出）· **S5 数据治理批次**（多维校验并行 → 回填 → 逐条断言验证，直接对应台账汇总/byRegion region_codes 清理/GREEN_GROUP 名称回填）· S6 多仓契约兼容验证 · S7 迁移升级批处理（JDK8→17）
- **第三层（与你既有治理体系咬合，价值最高）**：**S8 变更交付治理自动化**（把 catalog + Change 包 + 三态门从人肉检查变成机器执行 + 门禁判定 + 留档）· **S9 交付审计报告**（证据链装配成可贴 PR / 可进周报的交付物，零引擎改动）
- **第四层（外延）**：故障复盘多路调查 · 技术选型调研 · 知识库一致性治理 · 兼容性矩阵验证 · 汇报材料聚合

### 差异化独占场景（软编排结构性做不到）

三个硬性质划出独占区：
1. **真实终端隔离** → 兼容性矩阵验证（同一改动在 JDK8/11/17 并行验证，每 pane 可指不同 Docker/JDK/worktree）、交互式 CLI 驱动任务、长时任务+中途人工介入
2. **确定性拓扑** → 合规/生产变更（dry-run 能回答"这次会执行哪些步骤"）、团队流程固化
3. **证据链留档** → 受审计的数据变更（快照 + 500 条事件 + 逐条断言证据 = 可追溯审计档案）

**定位一句话**：软编排卖"AI 帮你把活干了"；PaneFlow 卖"活在一个你能看见、能干预、能留证的封闭环境里被干完了"。边界更窄，但边界内无替代品。

### 建议先做的三个场景

1. **S9 交付审计报告**（零新引擎能力，直接产出可交付物，对位"交付治理负责人"岗位职责）→ 再扩成 S8
2. **S5 数据治理批次**（对应手上真实任务；断言证据链价值密度最高；顺带首次用起闲置的 checks 能力）
3. **S1 多仓并行交付**（拓扑已存在，只差提示词与参数接通）

**共同前置只有一件**：给骨架加 `variables` 声明（今天只做了 1/8）——**没有参数，骨架永远是演示**。

### 盘点结论
**连接（4 个）**：Herdr（内建）、GitHub（凭据 + 模板同步）、模型网关（OmniRoute）、飞书。
**出站通道（1 个）**：仅飞书。`http.ts:288` 硬校验域名白名单（`open.feishu.cn|open.larksuite.com`），`notifier.ts` 硬编码飞书消息体 `{msg_type:'text'}`。
**入站通道（0 个）**：无 webhook 接收、无定时触发 → **自动化目前只能手动点「运行」或调 `/api/dispatch`**。

### 跟踪管道的三处断点（关键发现）
1. **埋点太稀**：`engine.ts` 的 `recordEvent` 只有 **4 处调用**（断点续跑 / 节点结束 / 指令提交 / 人工检查）；`RunEvent` 定义了 5 种 type，但 **`child` 与 `snapshot` 从未被使用**。
2. **前端零消费**：`/api/runs/:id/events` 端点就位，但 `packages/web/src` 里**没有任何地方调用**（`api.ts` 也无对应方法）→ 用户完全看不到时间线。
3. **通知太粗**：触发点只挂在 `engine.onChange`（`http.ts:638`），只看 3 个终态（blocked/completed/failed），无节点级事件；`notified` Set **只增不清**（内存泄漏）且重启即失效。

### 给出的四条路线（待用户选）
1. **事件总线化**（低风险）：补埋点 + 修 `notified` 泄漏。
2. **时间线 UI**（零引擎改动）：前端消费 events + WS 推增量 → 兑现"明厨亮灶"。
3. **通道层**（直接回应用户"更多连接和通道"）：`notifier` 抽成通道插件（通用 Webhook / 飞书 / 企业微信 / 钉钉 / 邮件），设置页新增「通道」区（多通道 + 每通道事件订阅 + 模板 + 测试发送），并迁移旧 `feishuWebhook`。
4. **入站自动化**（高价值高成本）：Webhook 入站（GitHub/CI/工单，需签名校验）+ cron 定时 → 从"点开始"变"事件驱动"。

**建议排序**：1+2 合并为一期（通道要推什么，取决于事件粒度），再做 3，最后 4。
