## 竞品对照：pi 生态的两个编排包（实地读源码后结论）

用户提出「pi-dynamic-workflows / pi-herdr-agents 感觉更灵活」，实际读包后的定位判断。**结论：灵活是真的、且是有意为之；但两者换掉的是「可复现 / 可预审 / 可追责」。**

### 事实基线（已核实，非猜测）

**`pi-dynamic-workflows@1.0.1`**（作者 Michaelliv，npm，`~/.pi/.../npm` 未安装，本次 `npm pack` 到 `/tmp/pi-dw`）
- pi 扩展，注册 `workflow` 工具：**模型现场写一段 JS 脚本**，脚本里用 `agent()/parallel()/pipeline()/phase()/log()/args/budget` 扇出子代理，返回前最后 `return` 汇总。
- 脚本跑在 Node `vm` 沙箱；AST 校验：`meta` 必须字面量，禁 `Date.now()`、`Math.random()`、`require`、`import`、`fs`、网络。
- 结构化输出用 JSON Schema → `structured_output` 工具 + `terminate: true`（**终止式工具调用**：不产出就结束不了）。
- 子代理是 `SessionManager.inMemory(cwd)` 创建的**内存 pi 会话**（`src/agent.ts:64`）→ 同进程、同文件系统、同用户权限，**无 pane、无进程隔离**。
- `isolation?: "worktree"` 与 `agentType` **只存在于类型/schema 声明**：全包 grep `worktree` 仅命中 `types/workflow.d.ts:37` 与 `src/workflow.ts:46` 两处声明，**0 处消费**（`agent.ts`/`workflow-tool.ts`/`extensions/` 均为 0 命中）→ 传了等于没传。
- README 自述：*"This is a prototype... does not yet implement persisted or resumable runs, or a `/workflows` manager."*

**`pi-herdr-agents@1.7.0`**（作者 giuseppecrj，**本机已装**在 pi 扩展目录）
- pi 扩展：把子代理跑在**真实 Herdr pane** 里，`subagent()` 立即返回（非阻塞），支持并行、单轮可中断而不销毁会话、受管 git worktree、`/worktree` 会话交接、内置 7 个角色（scout/planner/worker/reviewer/adversarial-reviewer/visual-tester/poteto）+ 可安装 role pack、persistent specialists。
- 依赖 `HERDR_ENV=1`（必须从 Herdr 内启动 pi），不支持其他 multiplexer。
- 自述限制：*"Worktrees isolate Git checkouts, not processes or permissions"*；*"Children are leaves by default; the parent owns integration and final verification"* → **父 pi（LLM）是协调者**。
- `skills/orchestrate/SKILL.md` 明说：唯一**强制**的是角色 frontmatter 的 `tools:` 允许清单；其余（子代理不得再派生、只读用途、依赖写串行、每次波次前重校 SHA 指纹）**全是提示词纪律**。

### 轴对轴结论

| 维度 | dynamic-workflows | herdr-agents | PaneFlow |
|---|---|---|---|
| 谁定拓扑 | 模型现场写脚本 | 父 LLM 现场拆解 | **用户策展、落文件** |
| 拓扑可复现 | 脚本可存，默认每次重生成 | 无显式图 | 图即文件，可 diff/版本化/钉住 |
| 隔离 | 内存会话（无） | Herdr pane + worktree（仅隔离 checkout） | 1 节点 1 pane（cwd/env/session 硬隔离）+ worktree |
| 失败语义 | `parallel` 仅保序 | 提示词里「依赖写串行」 | **引擎强制** requireAll/onFail/condition/retry/锁队列/resume |
| 产物契约 | JSON Schema 终止式工具调用（强） | 角色 md + 证据指纹（靠人） | `.herdr/artifacts/<nodeId>.json` 约定（**agent 常不写，有 output-fallback 兜底**） |
| 持久化/审计 | README 自述未实现 | session 保留，无跨运行审计 | run.events + 快照 + 导出/归档 + 时间线 UI |
| 载体中立 | 仅 pi | 仅 pi + 仅 Herdr | 17 种编码 Agent |

### 判断（写进产品判断，别丢）

1. **重叠最危险的是 `pi-herdr-agents`**：同一 Herdr 底座、同样 worktree 故事、已装在本机。PaneFlow 的**引擎层已不是护城河**；护城河只能是「策展骨架库 + 证据链交付物 + 可视化干预界面」。
2. **风险点**：若 herdr-agents 补上「持久化 run + 产物契约」，PaneFlow 的引擎优势基本蒸发 → 与项目自身诊断一致（**缺口是内容不是能力**）。所以骨架库加 `variables` 的优先级高于任何引擎改动。
3. **该偷的四样**（按价值排序）：
   - ① 产物 → **终止式结构化输出**（把「约定写文件」升级为「不产出就结束不了」，让 `output-fallback` 从兜底降级为告警）；
   - ② condition/variables 表达式加 **AST 校验 + 禁非确定性**（Date/random/环境读取）；
   - ③ 引入 `phase` 概念：运行时声明阶段，时间线按阶段分组而非平铺（现在是事后录制）；
   - ④ 角色改用 `.md` 定义 + 可安装 role pack（比薄壳 Role 更易共享）。
4. **不要做的事**：别去拼「AI 现场生成 DAG」——那正是它们的优势区，且会毁掉 D3 红线与审计卖点。
5. 话术改写：从「我能编排」改成「**我的编排跑之前你能看、跑完你能签字**」。

## 产品发散：多机聚合 + 移动端（用户提出「中间连接器 / bot 协作 / 小程序优先」）

**用户原始构想**：A 机与 B 机各装一个 PaneFlow、各自有不同 bot，通过一个「中间连接器」统一连上并下发指令；手机端优先做小程序。

**判断**：核心痛点是真的（用户确实有公司 Windows 机 + 个人 Mac 两台），但提法有三处要改。
- ✅ 值得做：**跨机聚合** + **移动端下发/审批**。
- ⚠️ 术语：「bot 协作」实际要的是**节点归属（placement）+ 跨机 run**；「中间连接器」应是**薄寻址层 + peer 联邦**，不是新的编排层。
- ❌ 不合理：① 中间层兼做调度（会出现两个引擎、两个权威源，证据链断裂）② 小程序作为首选载体 ③ 在修掉鉴权缺口前把 PaneFlow 暴露到任何外部网络。

**实地核实的四条架构结论（决定改造边界）**
1. **接缝已经存在**：`packages/server/src/orchestrate/herdr-ops.ts` 的 `HerdrOps` 是接口，`RealHerdrOps` / `FakeHerdrOps` 两个实现都注进引擎（`engine.ts:73` `private readonly ops: HerdrOps`）→ 跨机只需写第 3 个实现 `RemoteHerdrOps`，**引擎零改动**。且接口里 `target` 是字符串 → 可编码成 `peerId:paneId`。
2. **唯一强制 WS 的成员**：`subscribePaneStatus(paneId, cb)` 是「带回调的推送订阅」→ 远程实现必须走 WS，不能纯 REST（REST 只能轮询）。
3. **真正的边界在 worktree**：`createWorktree` 是 engine 的**私有方法**（`engine.ts:1170`），用 `execFileSync('git', ['-C', repo, 'worktree', 'add', ...])` **在本地**执行，路径写死 `os.tmpdir()/paneflow-wt/<runId>-<nodeId>`。→ 跨机时节点在 B 机执行、cwd 却指向 A 机的本地路径，**目录不存在**。所以「建/收 worktree」必须从 engine 移到执行机侧（并入 ops 或新的 peer-ops）。
4. **引擎单机内存态**（`engine.ts:58-70`）：
   - `blockedWaiters`（进程内 promise resolver）→ **好消息**：waiting/审批都在 coordinator（引擎只在一台机），所以**手机端审批只需连 coordinator 一台**，不必路由到执行机。
   - `repoClaims`（进程内 Map）→ 同一个 run 内的同仓并发**仍被正确串行**（因为调度只发生在一处）；但**跨 run / 跨 coordinator 无互斥**（两台机可各建各的 worktree、各推各的分支，冲突在 push 时才炸）。
   - `liveWorktrees`（内存态）→ 已知孤儿 worktree 缺口会**翻倍**，必须先修（并入 `recoverOrphans`）。

**移动端载体阶梯（建议顺序，均复用已有资产）**
- P0 零新框架：现有响应式 UI + PWA + 走 Tailscale 直连；看板 + 审批。
- P1 复用 `api/channels.ts`：飞书/钉钉**交互卡片**（blocked → 卡片带「放行/终止/补充指令」按钮 → 回调 `/api/runs/:id/nodes/:n/approve`）。这与既定的"入站自动化"阶段天然合流。
- P2 小程序：只做「看板 + 审批 + 选模板」，不做画布。硬前置=鉴权（`/input`、`/keys` 能远程敲回车/ctrl+c）、强制 TLS、peer 白名单。

**最有价值的发散形态**：**跨机 × 跨模型的对立审查** —— 把 reviewer 节点放到另一台机/另一个模型家族，天然避免同模型自审；与 herdr-agents 的 adversarial-review 同一洞察，但**它是拓扑里被策展、可复现、可审计的节点**，且直接产出证据链。可作为差异化卖点。

## 概念对齐：Grok Bot 的「多 Bot 协作」vs PaneFlow 的「多 Agent DAG」

用户澄清上一轮理解有误——他要的是「**bot 是可定义的主体，多个 bot 能协作**」这个层面的对照（不是多机部署）。

**像在哪 / 不像在哪（关键）**：像的是「多主体分工」，**不像的是「谁定分工」**。xAI 官方原文（`x.ai/news/designing-grok-bot`，Designing Grok Bot for a world of persistent agents）自述协作形态是**涌现**的："We saw one answer emerge as people created more Bots"；PaneFlow 的分工是**声明**的（DAG 落文件、可 diff、可 dry-run）。**这就是 D3 红线的另一种表述**。注意：不要把"涌现"当缺陷去补，那是两条产品线的选择。

**Grok Bot 原文中最值得抄的一条设计原则**：*"Capabilities and context therefore follow different boundaries... Tools and Skills live at the account level because many Bots may need to browse the web, work with documents, or send email. Memory and Routines belong to the Bot because they reflect what that particular role knows and does over time. Put another way, capabilities can be shared broadly while context remains with the role that needs it."*
→ 对位：**账号级** = `agentKind`/`env`/模型网关；**Bot 级** = `prePrompt`/知识文档/产物/记忆。PaneFlow 现在没有这条分层，一切都混在节点 config 或 Role 里。

**已核实的差距**（读代码确认，非推测）
- `packages/server/src/orchestrate/roles.ts:4` 的 `Role` = `{id, name, agentKind?, prePrompt?, env?}` —— **5 个字段**，装不下工具白名单/知识/记忆/输出契约。
- `routine` / 记忆 / 持久主体 在 `packages/server/src` + `packages/shared/src` 里**零命中** → 无任何对应概念。

**Grok Bot 其他可借鉴点**
- **Routines**：*"a standing responsibility that runs on a schedule or in response to an event"*，且 *"A prompt can start a session, but so can a schedule, an event, or another Bot"* → **与"入站自动化"阶段完全重合**，应把它从「cron 跑模板」重新定义成「给 bot 一个常驻职责」。
- **群聊** = 共享项目上下文 + 各 Bot 保留专有记忆 → PaneFlow 只有 `extra.tasks` 扇出 + merge 汇聚，**缺 run 级共享工作区**（artifact 黑板只是雏形）。
- **刻意限制**：约 **50 Bots/账号、6 Bots/群聊**。原文的判据：*"Did this help someone delegate, or did it give them one more thing to manage?"* → PaneFlow 的 DAG 无任何认知上限。
- **Chief of Staff 模式**：由一个协调 bot 做日常路由，只在需要判断时找人。PaneFlow 用**引擎**做路由（比 bot 更确定）→ 这一点 PaneFlow 更强，但可抄「产出一份人话交接摘要」。
- **"消失的界面"**：他们移除了面板/元数据，因为"每个都让用户多一件要管的事"。**PaneFlow 的画布正是面板** → 这是两条产品线目标函数的差别：他们优化"少管事"，PaneFlow 优化"留证据"，不该抄。

**反向（PaneFlow 有而它给不了的）**：拓扑可复现且**人设也能版本化**（能回答"上周那次审查用的是谁"）；真隔离、代码不出门（它是云端每 bot 一个迷你 VM）；结构化证据（AC-N 机器可校验）而非给人看的异构 transcript；不依赖 $120–300/月订阅。

**收敛建议**：把「Bot」正式引入为一等对象，但**只做 Grok Bot 没做的那一件事——Bot 定义落文件、可钉版本**。① `Role` → `Bot`（加 tools/knowledge/outputContract/memoryScope）；② 加 Routines（并入入站自动化）；③ 节点用 `bot:` 引用而非内联 prompt。这是唯一能同时打"更灵活"和"更可审计"两张牌的位置。
